# ADR-002: SHA-256 Instead of Argon2id for Machine-Generated Secrets

**Status:** Accepted
**Date:** 2026-07-03
**Phase:** 1.3.1 — Cryptographic Utilities

---

## Context

Two categories of secrets exist in this system:

1. **Human-chosen passwords** — created by a person and therefore drawn from a small, predictable space (dictionary words, common patterns). Must resist offline brute-force and rainbow-table attacks.
2. **Machine-generated secrets** — created by a CSPRNG (`secrets.token_hex(32)`) with 256 bits of true randomness. The search space is 2^256.

Master Tokens and Refresh Tokens are in category 2: they are generated by the server's OS CSPRNG and never chosen by a human.

The question is: should their hashes be stored using a memory-hard KDF (Argon2id, bcrypt, scrypt) or a fast cryptographic hash (SHA-256)?

---

## Decision

**Store SHA-256(token) for Master Tokens and Refresh Tokens.**

```python
hashlib.sha256(token.encode()).hexdigest()
```

Comparisons are always performed using `hmac.compare_digest()` (constant-time).

---

## Consequences

**Positive:**
- SHA-256 computation takes ~microseconds. At 500 login requests/second, SHA-256 adds ~0.5ms of total CPU load. Argon2id at secure parameters (m=64MB, t=3, p=4) would add ~300ms per request and ~96GB/s of memory bandwidth — catastrophic under modest load.
- Cryptographic correctness is maintained: with 256 bits of CSPRNG entropy, offline brute-force against SHA-256 hashes is computationally infeasible regardless of attacker GPU budget. A 2^256 search space makes dictionary attacks, rainbow tables, and brute force universally impossible.
- Simpler implementation with fewer dependencies (no Argon2 library required).
- Constant-time comparison (`hmac.compare_digest`) prevents timing side-channel attacks during verification.

**Negative:**
- If a developer reuses this hash pattern for a human-chosen secret (e.g., a user-set PIN, admin password), SHA-256 would be dangerously insecure. This distinction must be preserved in all future code review.

---

## Alternatives Considered

### Argon2id
**Rejected for machine-generated secrets.** Argon2id is the correct choice for human-chosen passwords. For 256-bit CSPRNG secrets, it provides zero additional security at enormous CPU and RAM cost. The security gain of memory-hardness is relevant only when the attacker can enumerate a meaningful fraction of the input space — 2^256 is not a meaningful fraction of anything.

### bcrypt
**Rejected.** Same reasoning as Argon2id, with the additional limitation that bcrypt truncates inputs at 72 bytes — harmless for passwords but conceptually wrong for binary tokens.

### SHA-512
**Not selected.** SHA-512 would also be correct. SHA-256 was chosen for consistency with the existing security ecosystem (SHA-256 is used in TLS 1.3, Ed25519, and is universally available). The additional output length of SHA-512 provides no security benefit here since the search space is bounded by the input entropy (256 bits), not the hash output length.

---

## Important Constraint

This decision applies exclusively to server-generated, high-entropy machine tokens.

If any human-chosen secret (password, PIN, passphrase) is ever introduced into the system, it **MUST** use Argon2id (or bcrypt as a fallback). This decision must not be cited as precedent for hashing human-chosen secrets with SHA-256.
